# FOMO 监控 · 网页版设计规格

日期:2026-08-22 · 状态:已确认,待实现

---

## 1. 要解决的问题

TG 推送擅长「实时提醒」,不擅长「看清楚 + 回头查」。三个具体缺口:

- **`/paper` 只显 15 条**(`bot.py` `copy_ledger(limit=15)`),而跟单台账已有 55 条 ——
  40 条在 TG 上永远看不到,「整体 0.6448x」这个结论在 TG 里根本得不出来。
- **没有任何地方能回答「跟着这个人买,我能拿到什么」**。这是用户看 PNL 的真实目的
  (确认过:是为了**判断单个信号值不值得跟**,不是为了围观别人赚多少)。
- 聚合类信息(排行、分布、健康度)在聊天流里表达不了。

**网页负责汇总与回溯,TG 继续负责实时提醒。两者不重叠。**

---

## 2. 核心指标:跟单价值

用户要的「PNL」经确认后落到这个指标上 —— 不是「这个人自己赚了多少」,
而是**「跟着他买,我能拿到什么」**。两者不是一回事:有人自己很赚,
但进场早、跑得快,跟着他反而接盘。

### 口径

对每个 (人, 币) 取该人**第一次买入**那条事件:

- `entry` = 该事件的 `fomo_events.market_cap`(**买入当时**的市值)
- `now` = `token_snapshot.market_cap`(当前)
- `peak` = `token_snapshot.max_market_cap`(峰值)
- 现价倍数 = now / entry;峰值倍数 = peak / entry

按人聚合:样本币数、现价中位数、胜率(现价 > 1x 的比例)、峰值中位数。
**样本 < 8 个币的人不给评分**(不是不显示,是不给排名 —— 样本太小的名次是噪声)。

### 实测(2026-08-22 快照)

45 人可评分,1145 个人币组合。峰值中位数区间 1.05x ~ 1.82x,胜率区间 14% ~ 62%。

| | 币数 | 现价中位 | 胜率 | 峰值中位 |
|---|---|---|---|---|
| Crissy | 20 | 0.74x | 45% | 1.82x |
| insentos | 13 | 1.12x | 62% | 1.58x |
| Momo | 28 | 0.51x | 32% | 1.61x |
| change | 8 | 0.65x | 25% | 1.05x |

⚠️ **45 人里只有 insentos 一个人的现价中位在 1x 以上。** 跟着名单里任何人买并拿住,
中位结果都是亏的。但峰值中位有真实区分度 —— 说明差别不在选币,在卖点。
页面必须把这两列**并排显示**,只显示其中一列都会误导。

### 零新增采集

全部来自现有 `fomo_events` + `token_snapshot`。

## 3. 架构

独立进程,`.\bot.ps1 --web` 启动,绑 `127.0.0.1:8420`(仅本机,已确认)。

```
bot.ps1 --run                    fomo.db (WAL)              bot.ps1 --web
poller + TG + 跟单   ──读写──▶                 ◀──只读──   网页服务
                                                            127.0.0.1
```

### 三条硬边界

1. **只读连接** —— `sqlite3.connect("file:...?mode=ro", uri=True)`。
   误写在驱动层被拒绝,不依赖自觉。
   ⚠️ 现有 `store.get_conn()` 打开的是**读写**连接,web 不能复用它。

2. **绝不调用 FOMO 接口** —— 登录令牌会自动续期并写回 `data/fomo_session.json`,
   两个进程同时续期会互相覆盖,把登录态搞坏。
   (同类事故已发生过一次:两个 poller 抢游标导致漏事件。)
   web 需要的线上数据一律由 poller 采集落库。

3. **绝不读 `data/` 目录** —— 那里有明文令牌(泄漏 = 账号被接管)、
   完整登录态浏览器 profile、含真实 userId 的探针响应。
   web 进程只认数据库文件一个路径。

### 为什么独立进程而不是同进程加线程

轮询间隔 15s,而 tick 实测 p50=6s / p90=12s —— 只剩 6~9 秒余量,且共享同一个 GIL。
一个慢查询就能吃掉 tick 的预算。独立进程还有三个好处:网页崩了监控照跑、
改网页代码不用停监控、只读是物理保证而非约定。

### 技术栈

**标准库 `http.server.ThreadingHTTPServer` + 手写路由,零新增依赖。**

项目规范写着「不引入未经评审的第三方依赖」。只读、本机、约 8 个路由的规模,
Flask 省下的代码量不值得引 5 个包(Flask/Werkzeug/Jinja2/click/itsdangerous)。

前端:服务端渲染 HTML + 少量原生 JS。**不引入构建步骤,不碰 npm。**

## 4. 模块划分

```
src/web/
  __init__.py
  server.py     # ThreadingHTTPServer + 路由表 + 启动/关闭
  db.py         # 只读连接(唯一允许打开数据库的地方)
  queries.py    # 全部 SQL 聚合,纯函数,可单测
  render.py     # HTML 渲染,纯函数,输入数据输出字符串
  static/       # 一个 css 文件,不用 CDN
```

边界:`queries.py` 不知道 HTML 的存在,`render.py` 不知道数据库的存在。
两者都可以脱离 HTTP 单测。

## 6. 新增采集(唯一一处)

`GET /v2/leaderboard/following` —— **一个请求拿全 80 人**的 24h/7d/30d 盈亏。
`client.py` 已实现,`bot.py` 已在用。

- **每 20 轮拉一次**(15s × 20 = 5 分钟),落新表 `user_pnl_snapshot`。
  取 20 的理由:盈亏是慢变量,5 分钟粒度足够;而这个接口与 `_poll_feed`
  的降频路径同款,可以复用 `_tick_no % N` 的写法。
  ⚠️ 与 `_FEED_EVERY_N_TICKS = 6` 错开,避免两个低频任务撞在同一轮
- ⚠️ 该接口返回的是**关注列表顺序,不是排名**(实测 -39.96K 排在 +37K 前面),
  必须本地重排
- ⚠️ 只覆盖登录账号关注的人

这是 poller 侧的改动,不是 web 侧的。

## 7. 明确不做

- **任何写操作。** 尤其不做「买入」按钮 —— 真实下单唯一入口仍是 TG 确认按钮。
  web 上多一个买入按钮就绕开了唯一那道人工确认。
- **人级持仓。** 库里一行都没有(持仓只活在 poller 内存,tick 结束即丢),
  需要新表 + 新采集,本期不碰。
- **「点开看这笔交易」。** `tx_hash` 只有 81/14422 = 0.56%,做出来 99% 是死链。
  可以做「点开看这个币」—— `token_address` 100% 填充,且 `formatter.py` 已有
  FOMO / GMGN 链接构造。
- **鉴权。** 已确认只在本机访问,绑 127.0.0.1 即可。

## 8. 显示规则(从现有代码里已防住的坑抄来)

1. **缺失就整行/整格消失**,不打 "N/A" / "--" / "0"。
   判空必须用 `is None` —— `formatter.py` 明写 `amount_usd=0.0` / `holders=0`
   是**有意义的真实值**(清仓就靠 `📦 剩余 $0.00` 体现),`if not x` 会把它们一起吞掉。

2. **行情超 1 小时标 stale。** `token_snapshot` 只覆盖「名单里还有人持有」的币,
   清仓后冻住 —— 实测 **29.6% 的快照已超 3 天**。现有 `_STALE_MCAP_MIN = 60`
   与 `SNAPSHOT_FRESH_MIN = 60` 是同一道线,沿用。

3. **`fomo_events.market_cap` 是「当时市值」,绝不能 JOIN 快照回填成「现在市值」。**
   混用会凭空造出纸面盈利。另外 **SELL 行的 market_cap 是卖出时市值**,别标成买入价。

4. **所有聚合数字标「按当前快照」。** 实测相邻两轮之间整体倍数 0.6544x → 0.6448x,
   单币 CONK 一个 tick 波动 7%。

5. **`token_symbol` 缺 31.3%**,可 LEFT JOIN `token_snapshot` 补 3273 行,
   残留 8.6% 按规则 1 处理(显示合约地址前若干位,不显示空白)。

6. **分链是 6 条不是 3 条**:solana / bsc / **robinhood(17.7%,常被漏)** /
   base / ethereum / monad。`store.py` 里那句「归一化后:solana / base / bsc」已过时。

## 9. 错误处理

- **web 的任何异常都不能影响监控** —— 本来就是独立进程,天然满足。
- 单个页面渲染失败返回 500 + 错误详情(本机自用,不需要藏),不整个服务挂掉。
- **读事务必须及时关闭。** 泄漏的读事务会把 WAL 钉住、无上限增长、全程静默无报错 ——
  这是本设计最隐蔽的风险。每个请求用 `with` 开关连接,不做连接池。
- 数据库被锁(`busy_timeout` 实测 5000ms,PRAGMA 覆盖了 connect 参数)时
  返回明确提示,不静默转圈。

## 10. 测试

沿用现有 pytest,跑在临时库上,不碰 `data/fomo.db`。

- **只读连接真的写不进去** —— 用临时库验证 INSERT 抛异常。这是最重要的一条。
- **聚合口径** —— 跟单价值/胜率/中位数算错了很难肉眼发现,必须钉死。
  包含边界:样本 < 8 不评分、entry 为 None 跳过、peak 缺失时回落现价。
- **渲染不因缺失字段崩溃** —— symbol/mcap/handle 各种缺失组合。
- **stale 标记** —— 超 1 小时标、够新不标(与 `/paper` 现有测试同款)。
- ⚠️ 不新增会真开浏览器或真发请求的测试。

## 11. 已知风险

| 风险 | 处置 |
|---|---|
| 读事务泄漏钉住 WAL,静默无报错 | 每请求 `with` 开关,不用连接池;加一条测试 |
| 具体数字是移动靶(整体倍数、排名都在抖) | 全部标「按当前快照」,不写死进文案 |
| `raw_json` 占库 52%(13.8MB/26.4MB),日增 2.4MB | 页面**绝不** `SELECT raw_json`;一年约 875MB,届时再谈归档 |
| 跟单价值样本窗口只有 11 天 | 页面标注数据起始时间;样本 < 8 不评分 |
| THESIS 采集有整天空洞(08-16 / 08-20 为 0) | 本期不用 THESIS 做 PNL 源 |
