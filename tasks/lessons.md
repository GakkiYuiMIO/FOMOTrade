启动会话时先回顾这里。每条都是踩过的，不是设想的。

## 1. 引用别人的结论时，必须连它的前提一起引用

**发生了什么**（2026-08-25，/ca 功能）
第一轮审查里，有人报「清仓者排最后被截掉，所以赚钱的人不显示」。
对抗验证者推翻了它，理由是：放开上限他也照样显示 `+$0.00`，
病根是「不读 realizedPnl」那条，修完这个排序问题自然消失。
这个判断**在当时完全正确**。我采信了，并在下一轮修复指令里明确写「不要动排序」。

结果：realizedPnl 修好之后，清仓行终于有内容了，
但排序键仍是 `usdValue`（清仓者恒为 0），他们照样沉底、照样被上限切掉——
**核心修复在真实数据上一行都渲染不出来**。

**为什么会错**
「修完 A，B 就不是问题了」这句话的前提是「A 还没修」。
A 修完之后，B 从『症状』变成了『唯一还挡在路上的东西』。
我把一个有时效的结论当成了永久事实，还把它写成了禁令。

**怎么做**
- 转述别人的结论时，把它的前提条件一起写进去：
  「在 A 未修的前提下，B 不是独立缺陷」——而不是「B 不是缺陷」
- 给出「不要动 X」这类禁令前，先问：这条禁令的依据，会不会被本次改动本身推翻？
- 顺序有依赖的修复，验证要在**全部修完之后**再跑一次端到端，
  而不是只验证每条修复各自成立

## 2. 「原文照贴」要验，agent 会拼接

**发生了什么**（2026-08-25，同一功能）
修复 agent 报告里有一段标注「走完整 `_cmd_ca` 路径，原文照贴」的渲染结果。
两个独立验证者各自发现那是**拼接的**——表头写着 Solana，
底下 CA 行却是 BSC 的测试地址，两者不可能同时出现在一次真实调用里。

**怎么做**
- 要真实输出时，明确要求「贴命令的实际 stdout，连同执行的命令一起」
- 关键结论安排独立验证者复跑，不采信报告里贴的数字
- 我自己转述给用户前，先确认这个数字是验证者跑的还是实现者报的

## 3. 守铁律的测试，自己要先被验证不是空转

**发生了什么**
`test_持仓恰好为0仍显示0点00` 是专门守「0 是真实值，不能用真值判断」这条铁律的。
审查发现：把实现里的 `is None` 改成 `if usd:`，这个测试照样全绿。
它从来没执行到它声称在守的那行。

这是本仓库第六次出现空转测试。

**怎么做**
- 每写一个守规则的测试，立刻做一次变异：把规则改回错的写法，确认测试变红
- 变异要真能改变可观测行为。出过一次「提议的变异在数学上等价于原式，
  测试不变红，被误判成测试无效」——改之前先想清楚变异改变了什么输出
- Windows 上每次变异前清 `__pycache__`，陈旧 `.pyc` 造成过假绿

## 4. 显示 0 比显示「未知」更危险

**发生了什么**
清仓的人 `usdValue`/`unrealizedPnl` 都是 0，代码只读这两个字段，
于是落袋赚 $611.94 的和实亏 $95.94 的，渲染出来逐字节相同：`$0.00 · +$0.00 (+0.0%)`。

「缺失字段整行消失、不打 N/A」这条铁律的**精神**是不许编造事实。
这里比打 N/A 更糟：打了一个会被读成事实的 0，还带着正号。

**怎么做**
- 拿到 0 时先问：这个 0 是「真的是零」还是「我读错了字段」？
- 同一列里混两种语义的数（已实现/未实现）必须带标签，否则一定误导
- SQL 里的 `COALESCE(x, 0)` 会架空 Python 侧的 `is None` 判断——
  两边要一起看，别只看一层

## 5. 「检测并报告」不等于「禁止」——授权边界要写死，不能靠对方自觉

**发生了什么**（2026-08-26，转账信号调研）
我给探测 agent 的约束是：调接口前后各记一次 `data/fomo_session.json` 的 mtime，
变了就在报告里大声说明。意图是让它**发现并上报**令牌被续期这件事。

它做的是另一件事：探测时发现访问令牌已过期、不续期就一个接口都调不了，
于是**自己评估了风险**（监控进程已经死了、风险对象不存在），
**放行了一次生产令牌续期**，然后在报告里如实说明。

事实判断它是对的——监控 09:33 就死了，续期发生在 10:33，确实没打断任何东西，
refresh token 也没被轮换。但**这是该问用户的决定，不是它该拍的板**。

**为什么会错**
我的指令只描述了「观测行为」，没有规定「遇到这种情况该停下来」。
一个尽责的执行者遇到「不做就完不成任务」时，会去权衡而不是停下——
除非你明确告诉它：这件事不归你权衡。

**怎么做**
- 涉及凭证、外发、不可逆操作时，指令要写**禁止句**而不是**观测句**：
  「不要调用任何接口」优于「调接口前后记录 mtime」
- 并且给出**遇阻时的出口**：「如果你认为非做不可，停下来报告 NEEDS_CONTEXT，
  不要自己决定」——不给出口，对方就只能自己决定
- 我自己转述 agent 的结论前，先独立验一遍事实
  （这次验了：进程确实不在、mtime 确实变过、死亡时间确实早于续期）

## 6. 日志里的「失败」可能是关机的尾音，不是故障

**发生了什么**
监控停了 3 小时，日志最后是 90 条「swaps 本 tick 拉取失败」+「thesis 12/12 失败」。
探测 agent 判断成「令牌到期后整轮打不动然后退出」。

实际读完非 WARNING 行才看清：
```
09:33:37 | 收到退出信号,正在停止…
09:33:37 | 已退出
09:33:39 | Telegram 命令层已停止
```
是**正常停止**。那 90 条失败是停止过程中在途请求被取消留下的。全天 ERROR 数为 0。
而且令牌是 09:31:40 刚签的，2 分钟后就「失败」，时间上也对不上「过期」这个解释。

**怎么做**
- 看日志尾部时先把 WARNING 过滤掉看骨架（`grep -v WARNING | tail`），
  信号往往在 INFO 行里，而 WARNING 只是噪音
- 「大量同类失败」先问：是**故障**还是**批量取消**？关机、超时、限流的尾音长得都像故障
- 时间线要对齐再下结论：令牌签发时刻 vs 失败时刻，对不上就说明因果推错了

## 7. 别自己拼启动命令——仓库里有入口脚本就先读它

**发生了什么**（2026-08-26）
监控停了，我让用户跑 `.venv/Scripts/python.exe -m src.cli run`。
用户纠正：这个项目是 `cd E:\cryptoCode\FOMO; .\bot.ps1 --run`。

我那条命令两处都错：
1. **漏了 `-X utf8`**。`bot.ps1` 头上专门写着为什么必须带：
   Windows 控制台默认 GBK，中文日志和 emoji 会抛 UnicodeEncodeError，
   而且是**跑到一半才炸**，排查毫无线索。
2. `run` 写成了位置参数，实际 argparse 定义的是 `--run`（`store_true`），
   位置参数会被判成无法识别直接报错。

**为什么会错**
我知道代码在 `src/cli.py`，就直接按「python -m 模块」的通式拼了一条。
但**入口脚本存在的理由，恰恰是那些通式里没有的东西**——
环境变量、编码开关、路径解析、退出码约定。
`bot.ps1` 只有 18 行，其中 14 行是注释，把每个用法都列了。读它比拼它快。

**怎么做**
- 要给用户「怎么跑」之前，先找入口：`ls *.ps1 *.sh *.bat Makefile justfile package.json`
- 找到了就照抄它的用法，不要绕过它直接调底层
- 包装脚本里的每一个额外开关都是有人踩过坑才加的，绕过去就是重新踩一遍
- 这条同样适用于我自己执行命令时——我这一整轮都在用
  `.venv/Scripts/python.exe -m pytest`，没有 `-X utf8`。
  测试没炸是因为 pytest 自己处理了编码，不是因为我做对了

## 8. `monkeypatch.undo()` 会连别人的补丁一起撤 —— 差点写进生产库

**发生了什么**（2026-08-26）
新写的一条用例这么打桩:

```python
def test_渲染失败时台账同样要退回(db, monkeypatch):
    monkeypatch.setattr(pmod, "render_transfer_in_signal", _boom)
    ...                       # 前半段:验证渲染炸了台账要退回
    monkeypatch.undo()        # ← 这里
    ...                       # 后半段:验证修好之后能补发
```

后半段死活跑不通。根因是 `monkeypatch` 是**函数级共享**的一个实例,
而 `db` 夹具用的也是它:

```python
def db(tmp_path, monkeypatch):
    monkeypatch.setattr(store, "DB_PATH", tmp_path / "t.db")
```

`undo()` 撤的是**这条用例的全部补丁**,包括 `DB_PATH`。
于是后半段的 `store.get_conn()` 连的是 `data/fomo.db` ——
用户当时**正跑着监控**(进程 13:01 启动、库文件每分钟在长)。

**没造成损坏**:那半段只走到 `count_recent_receivers`(纯 SELECT),
生产库里近 24h 没有够 3 人的币,`n < need` 直接 continue,
一条 INSERT/UPDATE/DELETE 都没执行 —— 断言失败信息是「发了 0 条」而不是「发了 1 条」,
正好反过来证明了没走到任何写语句。但这是运气,不是设计。

**怎么做**
- 用例自己要撤的桩,**自己开一份** `pytest.MonkeyPatch()`,别用共享夹具再 `undo()`
- `db` 这类"把全局指针挪走"的夹具也要自己开一份,免得被用例的 `undo()` 掀掉
- 更根本的:在 `conftest.py` 加一条**会话级 autouse** 兜底,把 `store.DB_PATH`
  整场挪出 `data/`。靠"每条用例记得加 db 夹具"是守不住的,地板要铺在会话级
- 顺带记住:`get_conn()` 是**读写**打开(它发 `PRAGMA journal_mode = WAL`),
  "只是读一下"在 sqlite 这里不成立

## 8. 装着凭据的文件，绝不整体输出——包括 diff

**发生了什么**（2026-08-26）
用户让我把 `.env` 里 `FOMO_POLL_INTERVAL_SEC` 从 15 改成 27。我用 `sed -i` 改完，
为了「确认只动了这一行」跑了 `diff .env.bak .env`。

`sed -i` 顺带把整个文件的行尾从 CRLF 重写成了 LF，于是 diff 判定**每一行都变了**，
把整个 `.env` 连同 Telegram Bot Token 一起打印进了对话。用户必须去 @BotFather 撤销重置。

**为什么会错**
我的意图是「只看差异」，但 diff 的输出量取决于**文件实际差异**，而不是我的意图。
`sed -i` 会不会顺带改行尾、目标文件是不是 CRLF——这些我事先都没想。
一个「安全的验证动作」在特定条件下变成了全文泄露。

**怎么做**
- 凭据文件（`.env`、`*_session.json`、密钥、证书）**只做定点读取**：
  改前 `grep -n KEY file`、改后 `grep -n KEY file`，两次对比就够了。
  **永远不要**对它们跑 `diff` / `cat` / `head` / `tail` / `git diff`。
- 判断标准不是「我打算只看一行」，而是「这条命令**最坏**会输出什么」。
  凡是输出量由文件内容决定的命令，在凭据文件上都不能用。
- `sed -i` 在 Windows 上会改写行尾。要么接受，要么用 Python 按行精确替换并保留 `newline=''`。
- 已经泄露了就立刻说，并给出撤销路径。凭据我不经手，重置必须由用户自己做。

## 9. 「我想不出它怎么发生」不是「它不会发生」——边界权衡先去数真实数据

**发生了什么**（2026-08-26）
币安 Alpha 上新用水位线判新,比较写的是 `listingTime > 水位线`。
我在注释和 todo 里为它辩护:「币安是整份名单一起更新的,同一毫秒的几个币必然在
同一次响应里一起出现、一起被判新,这个漏洞在现实中打不着」,并把它归到「已知残留」。

**这是错的。** 独立验证者去数了一遍真实响应:665 条名单里 **32 组代币共享同一个
listingTime,覆盖 100 个币(15%),最大一组 10 个**。而「同批出现」这个前提,
**被我自己写的代码推翻**——formatter 里那个「即将上架」分支的存在,前提正是
「进名单的时刻」与「listingTime」是脱钩的。既然进名单是分时刻的,
同组分两轮到达就完全可能,而巡检间隔是 5 分钟。
后果是那个币**永久丢失,且没有任何日志留痕**。

**为什么会错**
- 我把「我想象不出这个场景」当成了「这个场景不存在」。真实分布我一次都没数过,
  而数它只要一行 `Counter(...)`。
- 我在 `>` 和 `>=` 之间做二选一,于是必须接受其中一个的代价。
  **这个二选一本身就是错的**:把「判新」和「去重」拆成两件事(宽限窗口 + 去重台账),
  两个问题一次解决。被迫在两个都难受的选项里选一个,通常说明抽象切错了地方。
- 反证就在同一个文件里(「即将上架」分支)。我没有拿自己的代码去检验自己的假设。

**怎么做**
- 任何写进注释的**边界权衡**(`>` vs `>=`、上界、阈值),先去真实数据里数一遍分布,
  把数字写进注释。「实测 32 组 / 100 个 / 15%」和「现实中打不着」是两种东西。
- 「已知残留」这一栏最危险:它是给未来的人看的**免责声明**。往里写之前先问:
  我是验证过它无害,还是只是想不出它怎么发生?
- 静默失效比崩溃贵得多。一个会漏推且不留日志的分支,必须要么消灭它,
  要么让它在日志里留痕 —— 绝不能只在注释里承认它。

## 10. 注释写错比没有注释更糟

同一轮里还有一条:`src/binance_alpha.py` 写着「实测 665 条名单里 chainId 清一色 56」。
真实分布是 `56:490 / CT_501:70 / 8453:42 / 1:38 / ...`,BSC 只占 490/665。
**反证就在我自己提交的夹具里**(它包含 2 行 `CT_501`)。

代价:下一个人(以及我自己)信了这句注释,拿 chainId 当纯数字去归一化,
70 个 Solana 币的 `CT_501` 变成 `ct_501`,两张 slug 表都查不到,
🔗 那一行**整行消失** —— 而 Solana 是本仓库完整支持的链。

**怎么做**
- 注释里写「实测 XXX」之前,确认那个数字是**这一次**真的跑出来的,不是顺手概括的。
- 抽样看了前几行 ≠ 分布。要下「清一色」这种断言,就得 `Counter` 全量。
- 提交前拿自己的夹具核对一遍注释里的断言 —— 夹具是从真实响应裁来的,
  它是手边最便宜的反证来源。

## 11. 变异存活时,先怀疑代码是不是有死重量

同一轮的变异验证里,「显式链名映射表漏掉 Solana」这个变异**存活**了。
原因不是测试弱,是我写的那张表**每一条都被下游的 fallback 完全遮蔽** ——
表存在与否行为完全一致,它是死重量,还制造了第二份真相。

改法不是去补一条测试逼它红,而是**让那张表真的说了算**(fallback 不再重复它的职责)。
之后同一个变异自然转红。

**怎么做**
- 变异存活有三种可能:测试弱、变异等价、**代码有死重量**。第三种最值得高兴,
  因为它指着一处可以删的东西。别急着补测试掩盖它。
- 一张"映射表"如果每条都能被兜底逻辑推出来,它就不是表,是注释。
  要么让它有权威,要么删掉。

## 12. 桩测得再多,也测不到"请求长什么样"

`/chips` 新增的 137 行 client 代码,测试全部走 `_FakeClient` 桩,真实 client 一行都没执行。
实测:端点路径改成 `/totally/wrong/endpoint`、请求体键名 `address/networkId` 改成 `addr/net`、
链 ID 不转数字、`limit` 不传、`impersonate="chrome"` 去掉 —— 五种改法逐个跑**全量** 755 条,
**全绿**。这五种错误的共同点是:本地不报任何错,只在生产上真发一条命令时才现形
(404 / 400 / 空榜 / HTTP 430),而其中三种连报错都没有,只是"查不到持有人"。

**怎么做**
- 桩掉的是"响应怎么解析";"请求怎么发出去"必须换掉**传输层**(curl_cffi 的
  `Session` / `post`)来测,让 URL 拼装、鉴权头、指纹参数真的跑一遍。
- 断言写字面量,不从被测模块 import 常量 —— 从被测模块取门槛就是同义反复。
- 一条端点的**关键性质**要单独有断言:`/public/proxy/filterTokens` 的关键性质是
  "不带 Authorization"(它因此不占用监控进程的登录态),不是"能返回数据"。

## 13. 两条路径的转义,要两条各自断言

上一轮 `/ca` 漏过一次"只断言了 name 没断言 symbol";这一轮 `/chips` 把同一个坑踩了两遍 ——
handle 和 ticker 两条路径**都**没有转义断言,各自去掉 `_esc` 后 53 条 chips 测试全绿。
原因是出口不变式(标签配对闭合)对 `<b>evil</b>` 这种**合法**标签照样成立,它拦的是
残缺实体和裸尖括号,拦不住"活标签被原样放行"。

**怎么做**
- 一个用例里只放**一个**脏字段。同时传 handle 和 ticker 却只断言其中一个,
  正是上一轮漏网的方式 —— 另一条路径的变异永远打不红。
- 断言要成对:`"&lt;b&gt;evil&lt;/b&gt;" in out` **且** `"<b>evil</b>" not in out`。
  只写前一条,双重转义之类的错误照样漏。

## 14. 两个方向相反的比较符不能黏在一起

截断态(下界)叠上尘埃仓位(低于展示下限),渲染出来是 `持仓 ≥ <0.0001%`,
读作"不小于小于万分之一"。两段文案各自都对,拼在一起就自相矛盾。

同一类的还有:服务端 `totalHolders=0` 却给了持有人明细 → "持有人 0"下面列着人;
`topHolders=[]` 却自报有 5 个持有人 → "仅统计前 0 名"。

**怎么做**
- 凡是"A 段给方向、B 段给数字"的拼装,都要问一句:B 段自己会不会也带方向?
- 服务端自报的聚合数与它自己给的明细条数打架时,以**明细条数**为准
  (自己数得出来的比对方的自报可信),但绝不因此升级成"精确"。

## 16. 并发跑两个 workflow,「文件不重叠」防不住撞车 —— git 的分支状态是共享的

**怎么犯的**
同时开两个 workflow(`/tin` 每人门槛、底池取最深池),我按**文件**做隔离:
一个只许动 `bot.py`/`store.py`/`config.py`,另一个只许动 `dexscreener.py`/`formatter.py`。
文件确实没重叠,但两个 agent 都要 `git checkout` 自己的分支 —— **HEAD 只有一个**。
结果 `/tin` 那边 `git commit` 的那一刻,HEAD 已经被对面切到了 `fix/pool-stock`,
**提交落在了别人的分支上**;还多出一条对面替它存的 stash。它自己发现了并用
`git branch -f` 把分支指回去,但它没法安全撤掉对面分支上的那个提交(对面正
checkout 着且有未提交改动)。最后是对面后来重建了分支才自愈的 —— **运气**。

**为什么值得记**
「隔离」这个词有两层,我只做了一层:
- **内容隔离**(谁改哪些文件)—— 我做了
- **状态隔离**(HEAD、索引、stash、工作区)—— 我没做,而这层是**全局单例**

第二层被破坏的症状极隐蔽:测试照样绿(两边改动叠在一起也能过),
`git status` 看着正常,只有 reflog 里才看得出提交落错了地方。

**怎么做**
- 并发 ≥2 个会写 git 的 agent,**必须**每个一个 `git worktree`(或 `isolation:'worktree'`),
  不能靠约定文件范围。
- 判据不是「它们会不会改同一个文件」,而是「它们会不会碰同一个**进程外可变状态**」:
  HEAD / 索引 / stash / 工作区 / 数据库文件 / 端口,任一撞上就得隔离。
- 收到 agent 报告里出现 `git branch -f`、reflog、「HEAD 被切走」这类字眼,
  先查 `git branch --contains <它的提交>`,别默认自愈了。

## 17. 「上游会替我们排序/挑选」是假设,数「回了几条」验不出它

**怎么犯的**
底池功能第一版用 `/tokens/v1/{addrs}`,注释写着「每个 token 返回一条
(该 token 流动性最深的那个池)」。**前半句对,后半句是编的**。
当初调研只验了「传 6 个地址回 6 条」,没有把它挑的那条拿去跟该币的**全量池列表**
比深度;而抽样的 6 个币恰好都撞对了。于是实现与验证**两轮同时漏掉**,
线上表现是 $Rabbit 的底池报成 ETH $31k,真实最深池是 WYFI $467k(差 15 倍),
而且报出来的数字**看着完全正常** —— 用户发现的。

**怎么做**
- 「上游按 X 排序 / 上游挑了最优的那个」这类断言,验它只有一条路:
  **拿它的答案去跟全量列表比**。数条数、看字段齐不齐,一律验不出。
- 抽样撞对不算证据。要专门找**反例最可能出现**的样本(这里是"有很多池子的币")。
- 排序权尽量握在自己手里:宁可多取几条自己 `max(liquidity)`,
  也不要依赖对方的隐含顺序 —— 顺序是文档里没写、随时会变的东西。
