## Phase 0 实测结论（2026-08-11，已完成）

`--login` + `--probe` 已跑通，设计文档 §11 的字段假设被真实数据大幅修正：

### 根因级发现

| 发现 | 影响 |
|---|---|
| **`X-Supported-Chains` 必须是数字链 ID**（`1,56,143,4663,8453,1399811149`），不是链名 | 写错时服务端**不报错、直接把所有结果过滤成空数组**：swaps / trades / watchlist 全返回 0 条且 HTTP 200。这一个头就让整个项目看起来"能连通但没数据" |
| **响应统一信封 `responseObject`** | 不剥离则 `get_swaps()` 恒返回 0，而 `raw_get()` 同一请求能拿到 100 条 |
| **swap 是双侧扁平记录** `inTokenAddress` / `outTokenAddress` / `inHumanAmount` / `outHumanAmount` | 原按嵌套对象取，两侧都取不到 → 所有买卖降级成 `side_unknown` |
| **balances 顶层只有 `balance` / `tokenFilterResult` / `userToken` / `activeTrade`** | `_balance_key` 原按扁平结构取，恒返回 `(None, None)` → `count_holders` 一个都数不到、seeding 持仓回填整个失效 |

### 字段清单核对结果

- ✅ `#1 networkId`：有，**数字**（`1399811149` = Solana）。`swap` 顶层有，分腿还有 `inNetworkId`/`outNetworkId`——**存在跨链 swap**，聚合键必须用分腿的
- ✅ `#2 稳定 id`：`id` 字段稳定。**没有 txHash** → 兜底 hash 用不上，走原生 id 路径
- ✅ `#3 时间戳`：`createdAt` 是 ISO 字符串（`2026-08-11T05:55:04.720Z`）
- ✅ `#4 方向`：无显式 side 字段，靠**计价币位置**判定（设计 §6 的建模澄清正确）
- ✅ `#5 分页`：`tokenAddress`（按币过滤）+ `lastSwapIdV2`（游标），**不是 offset**
- ✅ `#9 均价`：`userToken.averageEntryPriceUsd`；成本 `currentCostBasisUsd`
- ✅ `#13 计价币`：白名单命中，无需补充
- ✅ `#17 Cloudflare`：带 Bearer 后全部放行 → **走轻量 `HttpFomoClient`**，不需要 Playwright 常驻
- ❌ `#8 交易次数`：swap 记录里没有 → **Q3 的否决票无从启用**，`judge_badge` 里那段注释保持注释
- ❌ `#11 转账`：端点语义是「我与该用户之间」→ **转入/转出砍掉**
- ⚠️ `#12 观点`：**没有按用户查的端点**（`/feed/user/thesis` 是 404）。改为「遍历持仓币 → 按币拉 `/feed/token/thesis` → 按 userId 过滤」，`afterTime` 单位是**毫秒**

### 端到端验证

真实用户真实交易跑通：🌱 首次建仓 / 🟢 加仓 / 🔴 卖出 三种徽章全判对，
同一个币第二次买入正确从 FIRST 变 ADD，共识计数与持仓/均价/市值全部正常。

### 真实运行后补充发现（用户实测自己的账号）

| 发现 | 症状 | 处置 |
|---|---|---|
| **`/feed/token/thesis` 必须显式传 `threshold=0`** | 观点功能完全不工作，且**无任何报错**。该参数按发帖人的**持仓美元额**过滤，不传时服务端用非 0 默认值 —— 响应里那个 `"threshold": 3.714...` 正好等于 `authorTrade.usdValue`。实测同一个币：不传 → 100 条里 0 条是目标用户的；传 `threshold=0` → 有 2 条。**大仓位能抓到、小仓位抓不到**，这种部分生效比全挂更难发现 | 固定传 `threshold=0` |
| 稳定币互换被渲染成「🟢 加仓 $USDC」 | USDT→USDC 兑换既不是建仓也不是离场，纯占屏 | `quote_only` 标志：落库但不推送。**落库时立即 `mark_sent`**，否则补发队列会每 20 秒捞一次、连捞 10 分钟 |

> 三个「HTTP 200、不报错、结果被静默过滤」的坑（`X-Supported-Chains` 用链名、
> 响应信封没剥离、thesis 漏传 `threshold`）合计吃掉了大部分排查时间。
> **教训：这个 API 对不认识的参数一律静默降级，不返回错误。**
> 以后遇到「能连通但没数据」，第一步就该用已登录的浏览器 profile 抓 App 自己发的请求做逐字段对照，
> 而不是逐个猜参数。

### 已知盲区

- **观点只能看到"监控用户当前持仓的币"下的**。他对已清仓的币发的观点看不到 —— 这是按币查的必然结果
- 链 `4663` 没有可读名，显示为数字

## 单轮提速（2026-08-11）

用户反馈「推送平均要 40s，能优化到 10s 内吗」。先剖析再动手，实测数据如下（69 人名单，含代理）：

| 端点 | p50 | 全员一轮 |
|---|---|---|
| `swaps` | 0.27s | ~5s |
| `balances` | 1.22s | ~35s ← 大头 |
| `trades` | 0.72s（尾部 4.7s） | ~20s |
| `thesis` 25 币（串行） | — | 4.1s |

并发拐点也很明确：69 人 × 3 端点，**12 线程 15.1s、24 线程 10.8s，36 线程反而 66.6s**——
服务端/代理打满后只会换来 504 和重试风暴。所以光加并发不够，必须砍请求量。

### 关键发现：`/feed/tradingActivity` 是「关注流」

探到一个原本没用上的端点。实测 100 条里 **100/100 都属于监控名单、名单外 0 个** ——
这是当前登录账号的关注流，不是全站流。单次 **0.25~0.43s**，100 条覆盖约一小时，
而且买/卖/观点三类混在一条流里。

于是把它当**变更检测器**：一次调用问出"谁刚动过"，再只给这些人拉 swaps。

⚠️ 但它只覆盖**已关注的人**。名单里若有没关注的人，动作永远不出现在流里 ——
所以必须保留 `SWEEP_PER_TICK=12` 的兜底轮转扫描。这不是优化项，是正确性要求。

### 改动清单

| 改动 | 效果 |
|---|---|
| 活动流当变更检测器 + 兜底轮转扫描 | 每轮 swaps 从 69 次降到 ~13 次 |
| `balances` 进程内缓存 + 有交易当场刷 + 8 个/轮轮转 | 每轮 balances 从 69 次降到 ~9 次 |
| `trades` 只拉有新动作的人 | 每轮从 69 次降到 0~2 次 |
| 调度单元从「一个用户」改成「一个请求」 | 慢端点不再占住整条线程 |
| 三个池合并成一个 + 观点扫描挪到后台线程并行 | 串行屏障从 4 道降到 2 道 |
| 推送节流改令牌桶（突发 5 条立发）+ notifier 复用连接池 | 6 条消息的等待从 17.5s 降到 1.5s |
| 重试退避加抖动、`_MAX_ATTEMPTS` 5→3、超时 25s→12s | 一次 504 风暴不再让整轮多花 15s |

### 结果

```
冷启动（建持仓缓存）  22.5s   每轮 API 调用 ~232 次 → ~46 次
稳态                 2.9 / 3.3 / 5.0s
```

轮询间隔随之 45s → 12s。端到端延迟从「45/2 + 40 ≈ 60-85s」降到「12/2 + 4 ≈ 10s」。

### 新增的教训

- **`dict.get()` 返回 None 有两种含义**：key 不存在 vs 值就是 None。
  balances 组装那段若写成 `bal_now.get(uid) or cache[uid]`，`[]`（清仓）会被当假值吞掉，
  那人就永远停在旧持仓上，「N 人仍持有」再也减不下去。必须显式判 `is not None`。
- **补漏池要按「第一池实际拉过谁」扣，不能按「活动流点过谁」扣**。
  冷启动时活动流点名集是空的，而第一池已经全员拉过一遍 —— 按后者扣会整整重打 69 次
  balances（实测 138 次），冷启动直接翻倍。
- **"拉取失败"与"本轮没排到他"必须分开**。混在一起的话稳态下每轮会对五十几个人
  各刷一条 WARNING；而且 `_swap_seen` 若把失败当成"这页就是全部"写进记忆，
  下一轮拉成功时那些条目会被当成"见过的"，这个人的新交易被永久跳过。
- **屏障比请求数更贵**。单个请求最慢能到 3~5s，四道串行屏障各付一次尾延迟，
  就是一轮里最大的一块。合并请求池 + 把观点扫描挪到后台线程，比继续砍请求数有效得多。
- **限流是真的**：该 API 2.5s 内连打 10 次会全部 429。加并发前先确认拐点在哪。

### 对抗性审查确认的三个缺陷（2026-08-11，6 视角 × 每条 3 个反驳者）

提速改完后跑了一轮多视角审查，24 条被反驳掉，3 条确认（去重后）——全部是这次改动引入的：

**1. `_bal_cache` 把「持仓索引延迟」冻结了一整圈（critical）**

有新交易的人，他的 `balances` 与 `swaps` 是**同一个池子里并发发出**的，
拿回来必然是服务端还没索引到这笔交易的旧持仓。这份最不准的快照进了缓存后，
下一轮他既不 hot 也多半轮不到轮转，错误状态被冻结整整一个轮转周期（约 9 轮 ≈ 108s）。

表现：名单集体抢同一个新币的那一两分钟里，「N 人仍持有」系统性偏小——
而那正是这个数字最该准的时刻。改造前每轮全员重拉，下一轮就自愈了。

> `count_holders` 里早就为买入方向写了 `+1` 补偿，说明这个索引延迟是本项目**已确认的事实**，
> 只是缓存把它从"只影响当轮"放大成了"影响一整圈"。

修法：`_bal_dirty` —— 本轮有新动作的人挂脏标记，下一轮无条件重拉一次。
⚠️ 两个信号都要收：`hot`（swaps 差集）**和** `feed_hot`（活动流）。
活动流通常更早知道这笔交易（它就是干这个的），那时 swaps 端点往往还没索引到、`hot` 是空的——
只认 `hot` 正好漏掉最需要补的那一类。（写测试时就是这么发现的。）

**2. 观点采集的后台线程让 playwright 每轮泄漏一套浏览器（critical，两个视角独立发现）**

`tick()` 无条件把 `_fetch_thesis_raw` 提交到每轮新建的线程池，
唯独漏了 `_fetch_snapshots` 里那道 `supports_concurrency` 守卫。
而 `PlaywrightFomoClient` 按 `threading.local` 私有创建整套 chromium、线程退出时不回收
——每 tick 泄漏约 300MB，12s 一轮几分钟吃光内存。

**这与文件注释里明令禁止、且早就修好过的是同一个故障，只是换了个入口进来。**

修法：`_start_thesis()` 统一收口——不可并发的实现留在主线程同步跑；
可并发的实现用**跨 tick 复用**的单线程池（顺带让 curl 会话跨轮复用，省掉每轮的 TLS 握手）；
`batch` 为空时连池子都不建。

**3. notifier 的 429 `retry_after` 没有上限（medium）**

`time.sleep(retry_after + 1)` 直接采信 TG 返回值，而这段 sleep 跑在 poller 线程的 `_dispatch` 里。
一个 `retry_after=300` 就把整个轮询堵 5 分钟，期间 `last_tick_at` 不前进、`/status` 看着像挂了。
`client._retry_after` 早就夹了 60s 上限，这条同类路径当初漏了。修法：夹同样的上限。

### 这轮审查的元教训

- **缓存的代价不是"数据旧一点"，是"把一个短暂的错误状态冻结住"。**
  引入任何缓存时，要问的不是"多久刷新一次"，而是"写进去的那一刻，值是不是恰好最不准"。
  这里就是：唯一会让持仓变化的动作（交易），恰恰保证了此刻拉到的持仓是错的。
- **同一个坑会从新入口回来。** playwright 的浏览器泄漏在 `_fetch_snapshots` 里有守卫、有注释、
  有教训记录，但新开一条后台线程时没人想起它。防线要建在**能力**上（`_start_thesis` 收口），
  不是建在**调用点**上。

### 追加:审查之后自己又发现的三件事

**4. 冷启动把全员挂成脏（写 `_bal_dirty` 的测试时暴露）**

冷启动那轮没有差集基准，`_hot_users` 会把**所有人**判成 hot——但那不是"所有人刚交易过"。
照单全收会让重启后的第二轮白白重拉一遍全员 balances（实测 2.4s → 5.9s）。
修法：`cold = not self._swap_seen`（必须在 `_hot_users` 之前取，那一步会把 `_swap_seen` 填满），
冷启动时只认 `feed_hot`。

**5. 401 落在最后一次尝试上会被降级成 `FomoAPIError`（自己复核审查的"已反驳"条目时发现）**

这条被 3 个反驳者判成"不成立"，但照着代码走一遍是真的：

```
attempt=1: 500 → sleep, continue
attempt=2: 500 → sleep, continue
attempt=3: 401 → auth_retried=False → invalidate + continue
           → while attempt(3) < 3 为假 → 退出循环 → raise FomoAPIError
```

而 `FomoAPIError` 会被 `_fetch_snapshots` 的 `except Exception` 吞成"该项降级为 None"，
tick 照常返回、`last_tick_at` 照常前进、`/status` 一切正常——正是 `_fetch_ok` 自己的注释里
写明"必须避免"的那种失效。**`_MAX_ATTEMPTS` 从 5 降到 3 是我这次改的，等于把这个坑变浅了。**
修法：记 `auth_status`，循环耗尽时若见过 401/403 就以 `AuthError` 收场。

> 教训：对抗性审查的"已反驳"不是免检章。反驳者只投票、不承担后果，
> 而这条的后果（监控静默死亡）严重到值得自己再走一遍代码。

**6. 429 雷群是真的会打起来（跑基准时被 monitor 抓到）**

同一毫秒 15 个请求一起 429（balances×10 + thesis×5 + trades×1），
服务端给的 `retry-after` 又完全相同，于是它们又在同一毫秒一起重试——把刚才那波压力原样重放。
之前两次基准"跑了 400s 没输出"就是撞上了这个。

根因是**峰值并发被低估**：观点扫描在后台线程、快照在主线程池，两者**同时在跑**，
真实峰值 = `fomo_fetch_workers(12) + _THESIS_WORKERS(8) = 20`，而实测拐点在 24 附近。
配置里却只按 fetch 池一处标了上限。

修法两条：`_retry_after` 加抖动（打散雷群的唯一手段）；
`_THESIS_WORKERS` 8→4、`_THESIS_TOKENS_PER_TICK` 25→12（有活动流之后这条路已经降级成兜底，
已关注的人发观点下一轮就直接推，不用等轮转扫到），峰值压回 16。

## 自己的交易/观点为什么慢(2026-08-12)

用户实测:「从 APP 下单到 TG 推送 30s 以上」「观点 10:05 发、10:09 才到」。

### 根因:活动流照不到自己

`/feed/tradingActivity` 是「**当前登录账号关注的人**」的流。而人不关注自己 ——
实测自己在 100 条流里出现 **0 次**。于是自己的动作只能靠兜底轮转捞:

| 类型 | 走的路 | 延迟 |
|---|---|---|
| 交易 | `SWEEP_PER_TICK=12`,70 人 → 6 轮 | 平均 36s、最坏 72s ← 用户量到的 30s+ |
| 观点 | 按币轮转,约 400 个币 / 每轮 12 个 | 约 6 分钟 ← 用户等了 4 分钟 |

同一个洞还影响另一类人:**名单里加过、但账号没关注的人**。

### 修法

探到 `/v2/users/current` 能拿到自己的 id(`/v2/users/me` 会被当 userId 校验报 400,
`/me`、`/users/me`、`/auth/me`、`/v2/profile` 全是 404)。于是:

```
_feed_blind = 监控名单 - 我关注的人      # 自然包含自己
```

- 这些人**每轮直拉**,不进兜底轮转 → 交易延迟 = 一个轮询间隔
- 他们刚碰过的币进「观点优先扫描名额」(`_THESIS_PRIORITY_SLOTS=6`,TTL 30 分钟)
  —— 观点几乎总是发在刚买的币上(实测 10:05 买入、10:05 发观点),
  优先名额让观点在下一轮就被扫到,而不是等轮转转过来
- 优先名额**占用**每轮扫描总量而不是叠加,峰值并发不变
- 关注列表缓存 10 分钟;拿不到时全员按"看不见"处理(慢但不漏)

轮询间隔 12s → 10s。端到端 ≈ 10/2 + 3 ≈ **8s**。

### 顺带修掉的两件事(都是压测时暴露的)

**冷启动多打 70 个 trades。** 冷启动的 `hot` 是"全员"(没有差集基准),
不代表全员刚交易过。照它补 trades = 启动瞬间 3N 个请求(70 swaps + 70 balances + 70 trades),
实测足以打爆限流窗口。冷启动改用 `feed_hot` 判定谁真的动过 → trades 70 → 20 次。

**活动流一失败就全员扫,是把限流越滚越大。**
活动流持续失败的头号原因就是**被限流**,这时候把请求量翻五倍只会更严重 ——
实测就是这么滚起来的:feed 429 → 全员扫 70 个 → 压力更大 → feed 又 429。
而活动流挂掉**并不会漏事件**:swaps 端点仍返回最近 50 笔,游标不推进 + `event_id` 去重
保证不丢不重,兜底轮转迟早扫到,只是晚几轮。
所以改成**扩大轮转**(3 倍切片,两轮覆盖全名单约 20s),而不是放弃增量。
效果:同一段压测里 429 从 14 次降到 3 次,稳态单轮从 6-9s 回到 2.3-3.2s。

### 限流的真实形态(实测)

| 端点 | 实测结论 |
|---|---|
| `/v2/users/{id}/swaps` | **27 req/s 打 40 个,0 个 429** —— 没有明显的每秒上限 |
| `/feed/tradingActivity` | 严格得多,2.5s 内连打 10 次全部 429 |

所以限的**不是每秒速率,而是一段时间内的总量,且按端点分别计**。
推论:不需要加限速器,该做的是**减少总请求量**(正是本次改动做的);
但活动流要省着用 —— 生产每 10s 一次(6 次/分)完全安全,
而压测时背靠背连打 4 轮 ≈ 生产 4 倍以上瞬时量,量到的是限流器不是 tick。
(之前两次"跑 400s 没输出"就是这么来的,已在压测脚本里补上真实间隔。)

### 回退:活动流不再当"变更检测器"(2026-08-12,同日)

上面那套「活动流点名 + _feed_blind + 兜底轮转」上线后,用户日志里 `/feed/tradingActivity`
**每一轮都 429**。查下去发现整个方案的前提就不成立。

**实测的限流形态(这是关键):**

| 端点 | 结论 |
|---|---|
| `/v2/users/{id}/swaps` | 27 req/s 打 40 个,**0 个 429** |
| `/feed/tradingActivity` | 每 10s 一次跑两分钟就持续 429(`retry-after: 0`,重试也没用) |

两个端点的限流**完全不是一个量级,且各算各的**。

**于是重新算这笔账:**

- 活动流省下的是「全员 swaps」——而实测 70 人 12 线程只要 **1.2~3.6s**
- 换来的是:那个端点的严格限流、"照不到自己"的覆盖盲区(用户实测 30s+)、
  以及为了绕开这两点堆出来的 `_feed_blind` / 兜底轮转 / 降级分支
- 更糟的是它**一失败就退回全员扫描**,请求量翻几倍 → 限流更严重 → 越滚越大。
  实测就是这么滚起来的:feed 429 → 全员扫 70 个 → feed 又 429

**结论:为了省 1~2s,买了一堆麻烦。回退。**

现在的形态,简单得多:

```
每轮:全员 swaps(没有例外、没有轮转、没有盲区)
      + balances(有交易的当场刷 / 上轮交易过的补刷 / 每轮轮转 8 个 / 其余读缓存)
      + trades(只给本轮有新事件的人)
      + 观点:按币轮转 12 个(后台线程,与采集并行)
              其中优先名额留给「刚动过的币」—— 观点几乎总是发在刚买的币上
活动流:降到每 6 轮一次,只负责捞"发在老仓位上"的观点。挂了完全不影响买卖推送
```

实测:冷启动 10.7s,稳态 **2.8 / 2.9 / 2.8s**(非常稳),429 从 14 次降到 4 次
且全部由带抖动的重试自愈。轮询间隔 10s → 端到端 ≈ 5 + 2.8 ≈ **8s**,每个人都一样,
不再有"自己反而最慢"这种事。

### 教训

- **省下来的是什么,换来的是什么,要放在一起算。** 活动流那条路单看"1 次调用替掉 70 次"
  非常漂亮,但省下的只有 1~2s,而代价是一个独立限流的端点 + 一个结构性盲区 +
  一套降级分支。删掉它之后,代码更短、更快、还没有盲区。
- **限流要按端点分别实测,不能只测一个就推广。** 先测 `/v2/users/*` 得出"27 req/s 没事",
  差点据此认定"不需要关心限流" —— 而真正卡住的那个端点严格几十倍。
- **降级策略不能反向加压。** "活动流失败 → 全员扫描"看起来是保守稳妥的兜底,
  实际上失败的头号原因就是限流,这个兜底恰好把火浇成了油。
  正确的做法是判断"失败会不会真的漏数据"—— 这里不会(游标不推进 + 主键去重),
  所以应该**降级得更轻**,而不是更重。

## 两个展示功能(2026-08-12)

### 特别关注 `/star`

`watch_users.starred` + `/star` `/unstar`,`/list` 里 ⭐ 的排最前、标题显示星标人数。

推送形态:`🌱 ⭐ 名字 (@handle) · 首次建仓 · 【$Plumber】`

⚠️ **星标不能顶到行首**。行首那个字符是聊天列表预览里唯一的扫描锚点,
⭐ 顶掉它之后所有特别关注的消息在列表里长得一模一样,买入卖出当场分不出来 ——
而那恰恰是最需要一眼看清方向的一批人。所以它跟在事件 emoji 后面。

⚠️ 星标是**纯展示**:不改徽章、不改共识分子分母、不改采集频率。
查询失败降级为"不打星标",绝不挡住推送。

**关于"彩色币名":Telegram 的 Bot API 不支持任意文字颜色。**
允许的标签只有 `b / i / u / s / code / pre / a / blockquote / tg-spoiler`,
没有 `font`、没有 `style`。真能出颜色的只有两条:
  1. diff 代码块(`<pre><code class="language-diff">`,加号行绿、减号行红)——
     但它是等宽的块级元素,会把标题行拆开,还吃掉行内链接
  2. 彩色 emoji(🟩🟥 这类)
所以默认用「加粗 + 方括号」做强调,颜色交给行首的 🌱/🟢/🔴 承担。
改样式只需要动 `formatter._style_symbol()` 一个函数。

### 币龄 `🕐 币龄 3H`

数据源:`balances[].tokenFilterResult.token.createdAt`(unix 秒)。**已经在每轮都拉的数据里,零额外请求。**

⚠️ 必须取 `token.createdAt`(**合约创建**),不是 `tokenFilterResult.createdAt`
(那是**交易对/池子**的创建时间)。两者对新币几乎一样,对老币差得离谱 ——
实测 USDC:`token.createdAt` = 2020-10-13(对),`tfr.createdAt` = 2024-03-20(某个池子建的时间)。
拿错字段的话一个老币会显示成"币龄 5D",而"新币"正是这个项目最关心的信号。

实测覆盖率 1058/1061 = 99.7%;抽查 USDt 8.7Y、WETH 8.7Y、USDC 8.0Y 全部与链上实际一致。

格式:`8M / 3H / 5D / 2MO / 1.4Y`。
⚠️ 分钟用 `M`、月份用 `MO` —— 单独一个 `M` 在币圈语境里会被读成市值。
⚠️ 落库(`fomo_events.token_created_at`):补发的消息也要能显示,
而 formatter 是纯函数不查库(§10.4 铁律 7)。币龄是恒定值,不像市值那样会过期。

### 教训

- **NaN 能绕过 `if x < 0`**。`fmt_token_age` 最初只挡负数,NaN 一路落到最后一支
  渲染成 `"nanY"` —— 单测当场抓到。范围判断遇上浮点必须显式 `math.isfinite`。
- **`to_row` 的字段集合有专门的单测钉着**。加一列 `token_created_at` 立刻红,
  提醒同步改 `insert_event` 的具名绑定 —— 这正是那条测试存在的理由。

### /hot 改成按倍数排序 + 首买人 + 基准市值(2026-08-12)

原来按买入人数排。问题是这个榜要回答的是「名单挖到了什么金狗」——
一个 60 倍但只有一个人买的币会沉到看不见的地方,而那恰恰是最该看到的。

新形态:

```
1. $Plumber · 🚀 66.9x · 👥 11 人买入(69 笔)
   💎 $41.90K → $2.80M · 💰 名单买入 $138.31K
   🥇 @brrrgrrrz 13 小时前首买
   👤 @remusofmars @collectible @Pasterniq +7
   🧬 Solana
   GCa9…
```

- 倍数放进标题行:它现在是名次的依据,排序键必须一眼可见,否则名次看着像随机的
- `💎 基准 → 现在` 把倍数的两个输入都摊开,用户能自己验算
- `🥇` 单独一行给首买人

SQL 改用 CTE + `ROW_NUMBER()`,让"首买人"与聚合共用同一套谓词
(active=1 AND stats_ready=1 + COUNTABLE_REASONS)——
不共用的话,首买人可能是一个根本没被算进 `👥 N 人` 的人。

⚠️ **`first_buyer` 与 `first_mcap` 可能不是同一行**,展示时必须分行写:
`first_buyer` 取真·最早那笔,`first_mcap` 取最早**且有市值**那笔。
市值只来自 balances,而 balances 快照晚于 swaps 索引 ——
"名单第一个人抢到新币"的那一刻他还没出现在自己的持仓里,那行的 market_cap 就是 NULL。
合成一句「@某人在 $42K 时买入」就是在断言一件我们并不知道的事。

⚠️ 算不出倍数的必须**显式**排最后:`ORDER BY (mult IS NULL), mult DESC, …`。
SQLite 里 NULL 在 DESC 中确实排最后,但依赖这个隐式行为等于把意图藏起来 ——
写出来,下一个人改排序时才不会踩掉。

副作用(已接受):单人小额买入的高倍币会冒到前排(如上面 #2,1 人 $474 买了个 11x)。
这正是用户想看的信号;`👥 N 人` 就在标题行里,判断权交给用户。

### /hot 再展开前 3 个买家(2026-08-12)

`👤 @a @b @c +7` 这一行只有名字,看不出谁下的注大、谁只是跟了一手。改成:

```
   🥇 @brrrgrrrz · $783.25(3 笔) · 13 小时前
   🥈 @remusofmars · $995.00 · 13 小时前
   🥉 @collectible · $4.99K · 4 小时前
   👤 另有 8 人 · 🧬 Solana
```

- 名次是**买入先后**,不是金额大小。榜里经常出现 🥈 比 🥇 买得多的情况
  (先摸到的人未必下注最重),所以页脚显式写了「🥇🥈🥉 = 买入先后」——
  奖牌通常被读成"金额最大",不点明就是误导。
- 金额是**窗口内累计**不是首笔:一个人分五笔建仓,只报首笔会把他的实际投入
  低报成五分之一,而"谁下的注最大"正是这一行的价值。
- 「另有 N 人」与链名合并一行,省掉一行高度。

⚠️ `HOT_TOP_BUYERS` 与 `MAX_HOT_ROWS` 是绑在一起调的:每多展开一个买家就是
每个币多一行,乘以榜行数直接顶 TG 的 4096 字符硬上限。
所以榜行数同步从 12 降到 10 —— 实测当前输出 2551 字符,留了足够余量。

## 启动刷 504 + Ctrl+C 退不掉(2026-08-12)

用户报了两个现象,是两个独立问题。

### 1. 启动时满屏 `FOMO 服务端错误 504 | …/balances`

两个原因叠在一起:

**(a) 冷启动把全名单的 balances 一次性打出去。**
`/balances` 是最重的端点(单个 100~400KB),70 个一起打直接把源站打到
**504 Gateway Timeout** —— 注意这是 origin 超时,**不是限流**,重试也是 504,
结果缓存反而填不满。
修法:`_BALANCE_WARMUP_PER_TICK=10`,分批预热。
⚠️ 预热要**轮转取**而不是每轮取头几个 —— 上游抖动时队头那几个会一直失败,
固定取头部等于让后面的人永远排不上,缓存永远填不满。

**(b) 每次重试都打一条 WARNING。**
上游一抖就是几十行刷屏,而这些失败**已经被处理掉了**
(重试 + balances 有缓存兜底)。真正要紧的 ERROR 会被淹掉。
修法:逐条降到 DEBUG,每轮汇总成一行:

```
上游抖动 | 服务端 504×9 · 最终降级 balances×1 · 还有 70 人的持仓未预热(已重试/降级,不影响推送)
```

实测同一段压测:WARNING 从 34 行降到 4 行,每行都有信息量。

> 顺带确认:这次的 504 是 **FOMO 源站真的在劣化** —— 同一个 `/balances`
> 早上 p50 1.2s,现在单次 10.4s。不是我们打太狠。所以单轮涨到 11-13s,
> 轮询间隔相应从 10s 调到 15s(贴着单轮耗时设会一直刷 skipped)。

### 2. Ctrl+C 要按很多次、等很久才退出

调度器停了,但线程池里几十个请求还在跑:每个可能卡在重试退避的 `time.sleep()` 里,
或者卡在 12s 的 HTTP 超时上。`ThreadPoolExecutor` 的 atexit 钩子会 join 它们
（用户日志末尾那段 `_python_exit → t.join() → KeyboardInterrupt` 就是它）。

修法三处:
- `client._STOP`(全局 Event)+ `sleep_or_stop()`:所有退避改成**可打断的等待**;
  已在停机则排队中的请求直接放弃、不再发出
- `poller._throttle_send` 同样改成可打断 —— 积压几十条时它一次要等好几十秒
- `Poller.close()` 关掉常驻的观点线程池;cli 的 `finally` 里**先喊停、再关调度器**

实测:从"发出停机信号"到"tick 收尾" **0.2s**(改之前要十几到几十秒)。

### 教训

- **"已经处理掉的错误"不该用 WARNING 逐条播报。** 判据是:这条日志能让用户**做点什么**吗?
  不能的话就降级 + 汇总。刷屏的真实代价是把能做点什么的那几行淹掉。
- **限量取批次时要轮转。** `[:N]` 看着人畜无害,但只要队头会失败,
  后面的人就永远排不上 —— 而"队头会失败"恰恰是限量的起因。
- **可中断的等待要覆盖所有以秒计的 sleep**,不只是重试退避。
  漏掉推送节流那一处,Ctrl+C 照样走不掉。

### /hot 前三名加"进场市值"(2026-08-12)

```
🥇 @brrrgrrrz · 💎$41.90K · $783.25(3 笔) · 15h
🥈 @remusofmars · 💎$98.25K · $995.00 · 14h
🥉 @collectible · 💎$4.19M · $4.99K · 6h
```

一眼能看出"谁在什么位置进的":🥇 在 $41.9K 摸到,🥉 进场时已经 $4.19M(涨了 100 倍)。
这是"跟谁"最直接的依据 —— 名次只说明先后,进场市值才说明这一手值不值得跟。

⚠️ mcap 取的是他**最早一笔有市值**的那笔,不是最早那笔。
市值只来自 balances、而 balances 快照晚于 swaps 索引 ——
抢到新币那一刻本人还没出现在自己的持仓里,那行 market_cap 就是 NULL。
不往后找的话,恰恰是"抢得最早的人"没有进场市值可显示,而那正是最该看到的一个。

⚠️ 多笔建仓时这个数只代表**第一笔**的位置,所以后面的笔数必须留着 ——
只看一个市值会把"分五笔从 40K 加到 200K"读成"他在 40K 一把梭"。

时间改成紧凑写法(`15h` 而不是「15 小时前」):一行要塞名字+市值+金额+时间,
四个汉字就是手机上换行的那根稻草。与币龄行用同一套单位。

### /hot 补峰值市值 + 「现在」两个字(2026-08-12)

用户看到 `🥉 @collectible · 💎$4.19M`,而那一行上面写着 `💎 $41.90K → $2.68M`,
于是问"第三名 4M 才进不应该吧"、"$2.68M 是 ATH 吧"。

查库之后两个问题都有明确答案:

**排序是对的。** $Plumber 的真实买入序列:

| # | 谁 | 时间 | 买入时市值 |
|---|---|---|---|
| 1 | brrrgrrrz | 14:20 | $41.9K |
| 2 | remusofmars | 14:31 | $98.3K |
| 3 | collectible | **22:54** | $4.19M |

@collectible 确实是第 3 个买的,但比第 2 名晚了 **8 个半小时** ——
只有两个人吃到早期,之后断档 8 小时,剩下 9 个人全在 $4.19M 附近一拥而上。

**$2.68M 是当前市值不是 ATH**(`token_snapshot.market_cap` 每轮从 balances 刷新)。
但用户的直觉指向了一个真问题:箭头 `$41.90K → $2.68M` 读起来像"起点 → 最高点",
于是 $4.19M 的进场看着就不可能。**真相是这个币冲到 $4.19M 之后回落了**,
追高那批人正套着 —— 而这恰恰是最该看见的信息,却被现在的显示藏起来了。

修法:
- 文案写明「现在」:`💎 $41.90K → 现在 $2.91M`
- 新增 `token_snapshot.max_market_cap`(每轮取 max,只增不减),
  明显回落过才显示:`· 峰值 $4.19M`
- ⚠️ 迁移**用历史买入记录回填**(`MAX(fomo_events.market_cap)`),不从今天开始重新攒:
  已经冲高回落的币恰恰是最该看到峰值的那些,而它多半不会再冲了 ——
  不回填的话它永远没有峰值可显示。`fomo_events.market_cap` 天然采样了上涨过程。
- ⚠️ 那一轮没有市值时不能把峰值抹掉:清仓后的币仍会被 trades 带进来,
  但那时 market_cap 是 NULL。

效果:

```
1. $Plumber · 🚀 69.5x · 👥 11 人买入(69 笔)
   💎 $41.90K → 现在 $2.91M · 峰值 $4.19M · 💰 名单买入 $138.31K
   🥇 @brrrgrrrz · 💎$41.90K · $783.25(3 笔) · 15h
   🥈 @remusofmars · 💎$98.25K · $995.00 · 15h
   🥉 @collectible · 💎$4.19M · $4.99K · 6h
```

一眼看出 @collectible 买在峰值上、现在套着 30%。

⚠️ 叫「峰值」不叫「ATH」:它只在名单里有人持有、且轮询到的时刻才采样,
币在我们看它之前冲过多高无从知道。名字必须诚实。

### 教训

- **用户说"这个数不对"时,先查库再解释。** 这次两个疑问一个是"其实是对的"、
  一个是"数是对的但展示有误导",处置完全不同 —— 靠猜会两个都答错。
- **箭头 `A → B` 天然被读成"起点→终点/最高"。** 中间回落过就必须显式写出来,
  否则下面任何一个高于 B 的数字都会被当成 bug。

### 倍数改成"最早买入 → 峰值"(2026-08-12)

原来倍数 = 现价 ÷ 最早买入市值。问题:这个榜要回答"名单挖到了什么金狗",
而金狗的价值在于它**跑出来过**多少 —— 一个冲到 100x 又回落到 60x 的币,
排在一个稳在 70x 的币后面是不合理的,前者才是那次真正抓住了的机会。

现在:`🚀 最高 99.9x`(峰值 ÷ 名单最早买入时市值),排序同样按它。

⚠️ 标题必须写「最高」两个字。不写的话,一个回撤过的币会被当成"现在还有这么多",
而下面 💎 行明明写着现价更低 —— 两个数打架,用户只会当成 bug。
⚠️ 现价照常在 💎 行里(`$41.90K → 现在 $3.16M · 峰值 $4.19M`),回撤自己看得见。

### 判定层的几个刻意选择

- **拿不到币龄 / 拿不到市值一律不跟**,而不是放行。这两个值恰恰是**新币最容易缺**的
  (都来自 balances,而 balances 快照晚于 swaps 索引)—— 放行等于筛选器专挑最该拦的放过去。
- **每日上限放在最后判**。放前面的话,达到上限之后所有币的原因都变成「已达当日上限」,
  就看不出哪些币其实本来也不合格 —— 而那才是调参数时要看的。
- **盈亏用市值比折算**,不记 token 数量。我们没有真实成交回执,记数量等于把滑点、
  手续费、成交价假装成理想值。市值比至少口径诚实:它就是"这个币涨跌了多少"。

⚠️ 执行器没接入时**明确写 failed**,绝不写 filled。

### 这次改造真正学到的

1. **审计说的不一定对,但审计问的一定值得查。**
   30 条发现反驳掉 20 条。存活的 10 条里还有 2 条的**理由**是错的
   (A1 说"库里很可能已经是 paper_only=False" —— 实际不是),但结论仍然成立,
   只是理由要换。所以「已反驳」不是免检章,「已确认」也不是。

2. **最好的数据源常常不在你先想到的那张表里。**
   A3 本来只打算把 snapshot 优先改成 balances 优先。是**测试挂了**才逼出
   真正的答案:买入事件自带 `market_cap`,那就是「名单里那个人刚刚是在什么价位买的」,
   比任何快照都准。84% 覆盖率,一行代码。

3. **加护栏的动作本身会拆掉别的护栏。**
   B3 把买家数查询挪到循环外做排序,顺手就把 A5 那道 per-token 兜底从背后绕过去了。
   当场被测试抓到。**改动的半径永远比你以为的大一圈。**

4. **「停」这个动作有一条不可逾越的线。**
   急停检查点绝不能出现在 `submit.click()` 之后。过了那一下,
   「停」只会让程序不去读回执 —— 钱花了、状态没写、你还以为停住了。
   同理:关闭时不能替在途单写 failed,对账时不能把 unknown 判成 failed,
   金额上限要把 unknown 按「花了」算。
   **不确定的时候,「可能花了钱」永远比「没花钱」安全。**

5. **措辞是功能的一部分。**
   「已成交」/「已点击待核对」/「未成交」必须是三档而不是两档:
   把第二档报成成功会让人以为没事,报成失败会诱使人手动再买一次。
   同理「今日 3/0 单」会被读成「已经限住了」,实际是闸门开着。
